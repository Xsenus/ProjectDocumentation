# Правила для агентов

## Git: ветки и Pull Request'ы

Обязательно для всех агентов (Codex, Claude Code) и людей. PR — Pull Request (в GitLab — Merge Request). Базовая ветка: `master`.

### Ветки
- Любое изменение — даже одна строка или документация — делается в новой ветке от свежей `master`: `git fetch`, затем ветка от `origin/master`.
- Одна задача — одна ветка. Имя — по схеме, принятой в репозитории, иначе `feature/…`, `fix/…`, `chore/…`.
- Перед созданием ветки проверь `git status`: чужие незакоммиченные изменения не трогай и не переноси в свою ветку — спроси.
- В чужие ветки, включая ветки другого агента, без запроса не коммить. Если Codex и Claude работают одновременно, у каждого своя ветка и свой worktree или клон.
- Прямые коммиты и пуши в `master` запрещены.

### Мерж — только через PR
- Изменения попадают в `master` только через PR. Запрещено: локальный `git merge` в `master` с последующим push, прямой push, force-push в общие ветки, мерж в обход защиты ветки (`--admin` и т. п.).
- Перед открытием PR прогони «Проверки перед PR». Не пиши, что проверки прошли, если ты их не запускал.
- В описании PR: что сделано и зачем, как проверено, есть ли миграции БД.
- Открыв PR, дождись результатов CI (`gh pr checks <номер> --watch` или аналог).
- PR вливается, только когда проверки зелёные (если CI нет — локальные), конфликтов нет и получены обязательные ревью. Способ мержа (squash / merge / rebase) — как принято в репозитории.
- Кто вливает: агент сам, через PR (`gh pr merge` или аналог), как только выполнены условия выше.
- Если для push или создания PR нужно подтверждение — запроси его. Если это невозможно (нет сети, прав или CLI), не обходи локальным мержем: доведи ветку до зелёных локальных проверок и в ответе дай имя ветки, заголовок и описание PR. Если среда сама создаёт ветку и PR (облачные задачи Codex и Claude Code) — пользуйся её механизмом.

### Если проверки (локальные или CI) или мерж не проходят
- Цель — зелёный PR за счёт исправления причины, а не обхода проверок.
- Читай логи упавших джобов (`gh run view <id> --log-failed` или аналог), воспроизводи падение локально той же командой, что в CI, ищи корневую причину.
- Исправляй код, а не проверки. Без явного разрешения пользователя нельзя: пропускать, удалять или ослаблять тесты; добавлять подавления ради зелёного статуса (`@ts-ignore`, `eslint-disable`, `# type: ignore`, `# noqa`, `#pragma warning disable`, skip у тестов); снижать пороги (покрытие и т. п.); править конфиги CI и линтеров, чтобы стало зелёным; коммитить с `--no-verify`.
- Тест устарел из-за намеренного изменения поведения — обнови его и объясни это в описании PR.
- Конфликты: подтяни свежую `master` в свою ветку, разреши конфликты, сохранив чужие изменения, снова прогони проверки. После rebase — только `git push --force-with-lease` и только в свою ветку.
- Исправления пушь в ту же ветку, новый PR не создавай.
- Падение не связано с твоими изменениями (то же падает на `master`, флейк, инфраструктура, секреты CI) — не маскируй его: перезапусти джоб один раз, не помогло — сообщи с диагнозом.
- После трёх циклов исправлений проверки всё ещё красные — остановись и опиши, что пробовал и в чём, по-твоему, причина.

### После мержа: удаление веток
- Удаляй ветку, только когда она полностью отработана: PR в статусе merged (`gh pr view <номер> --json state` или аналог), работы по ней не осталось и других открытых PR из неё нет.
- Удалённую ветку удали, если хостинг не сделал этого сам: `git push origin --delete <ветка>`.
- Локально: `git switch master && git pull --ff-only`, затем `git branch -d <ветка>`. После squash- или rebase-мержа git может отказаться — тогда, убедившись, что PR merged, используй `-D`. В конце `git fetch --prune`.
- Слитую ветку не переиспользуй: доработки и исправления после мержа — в новой ветке от свежей `master`.
- Никогда не удаляй `master`, защищённые и чужие ветки, а также ветки с открытыми PR или с коммитами, не вошедшими в слитый PR.

### БД и миграции
- Схему БД меняй только через миграции проекта (EF Core, Alembic, Django, Prisma, Flyway, Liquibase и т. п.), в той же ветке и том же PR, что и код.
- Из рабочей ветки ничего не применяй к общим и боевым базам.
- В этом проекте миграций нет: SQLite-база `xml.s3db` создаётся и обновляется автоматически средствами DevExpress XPO (`AutoCreateOption.DatabaseAndSchema` в `Core.NET/Controllers/SessionController.cs`) по классам `Core.NET/Models/XPO`. Изменения этих классов меняют схему у пользователей — опиши их в PR.

### Проверки перед PR
CI (`.github/workflows`) в репозитории нет, тестов и линтеров тоже нет — проверяй хотя бы сборку. Новые инструменты без согласования не добавлять.

Решение `ProjectDocumentation.sln` (.NET Framework 4.7.2, WinForms, DevExpress 24.2, пакеты через `packages.config`) собирается только на Windows с установленным и лицензированным DevExpress 24.2 и Visual Studio / Build Tools:

```powershell
nuget restore ProjectDocumentation.sln
msbuild ProjectDocumentation.sln /p:Configuration=Release /m
```

Если собрать негде (облачная среда, Linux, нет DevExpress) — так и напиши в PR, что сборка не запускалась, и не утверждай обратное.
