# Результаты проверки кода

Дата проверки: 09.11.2026, ветка `master` (коммит `a39449a`).

## Как проверялось

- Прочитан весь рукописный код обоих проектов: контроллеры, модели XPO, расширения, все формы, обёртки. В сгенерированных моделях `Conclusion.cs` и `ExplanatoryNote.cs` проверены корневые типы, коллекции и перечисления, на которые опирается код.
- Каждый дефект подтверждён трассировкой по коду: откуда приходит значение и куда записывается.
- **Приложение не собиралось и не запускалось**: проверка шла в облачной среде на Linux, где нет Windows, Visual Studio и лицензии DevExpress. Автотестов в проекте нет. Поэтому всё ниже — выводы статического анализа. Сценарии нужно подтвердить запуском на Windows перед исправлением.

Строки указаны по состоянию на коммит `a39449a`.

## Подробно

### D-01. Дублирование списков при повторном сохранении заключения — критично

`ProjectDocumentation.NET/Forms/ObjectChange/ConclusionEdit.cs`

- При открытии (`ConclusionEdit_Load`, например стр. 1663) коллекции модели **копируются** в приватные списки: `_tDocuments = Conclusion.Documents?.ToList()`.
- При сохранении (`btnSave_Click`) элементы списков **добавляются** в те же коллекции модели, которые никто не очищает: `Conclusion.Documents.Add(item)` (стр. 996). В файле нет ни одного `Clear()`.
- Так же работают `PreviousConclusions`, `Finance`, `Designer`, `EepdUse` (стр. 1196), `CadastralNumber`, `ProjectDocumentsDeveloper`, `ProjectDocumentsTechnicalCustomer`, `EngineeringSurveyDeveloper`, `EngineeringSurveyTechnicalCustomer`, `ExpertProjectDocuments`, `EngineeringSurveyAddress`, `ExpertEngineeringSurveys`, `Summary.EngineeringSurveyType` (стр. 1309) и `Experts` (стр. 1381).

Сценарии:
1. Открыть сохранённое заключение с тремя документами, нажать «Сохранить» — в XML шесть документов. Ещё раз — двенадцать.
2. Удалить документ из списка и сохранить: он остаётся в коллекции модели, удаление не сохраняется.
3. Нажать «Сохранить» с ошибкой в поле, которое проверяется после раздела I.5, исправить и сохранить снова — документы раздела I.5 добавятся дважды даже у нового заключения.

Исправление: перед заполнением каждую коллекцию очищать (`Clear()`) либо собирать модель в новый объект.

### D-02. Проверка обязательных полей не работает — критично

`ConclusionEdit.cs`: `GetCheckComboBoxItems` (стр. 2356), `GetEnumByAttributeValue` (2389), `GetStringValue` (2412), `GetValueGeneralizedDictionary` (2433).

- У всех четырёх хелперов `isNullAble = true` по умолчанию. Исключение с текстом «Заполните …» бросается только при `isNullAble: false`, а во всём проекте **нет ни одного вызова** с `isNullAble: false`. Все сообщения о незаполненных полях недостижимы.
- Незаполненный список даёт `null`. Тогда `GetEnumByAttributeValue<T>(null)` не находит совпадения и возвращает `default(T)`, то есть **первое значение перечисления**. Поля-перечисления в модели не nullable, поэтому это значение попадает в XML.

Примеры: не выбран «Результат экспертизы» → `ExaminationResult = Item1` (`"1"`, «Положительный»); не выбран регион → `"00"` («Объект расположен за пределами РФ»); не выбран вид работ → `"1"` («Строительство»).

Исправление: для полей, обязательных по XSD, передавать `isNullAble: false`. В `GetEnumByAttributeValue` при ненайденном коде бросать исключение или возвращать `T?`. Перед сохранением проверять XML по XSD.

### D-03. Перевод «код → enum» через повторную загрузку сборки — высокая

`ConclusionEdit.GetMethodName` (стр. 2160) на **каждый** вызов `GetEnumByAttributeValue`:
- ищет `Core.NET.dll` по относительному пути — в текущей папке или в `dll\`, иначе бросает «Не найден Core.NET.dll.»;
- загружает сборку через `Assembly.LoadFile` во второй контекст и перебирает все её типы рефлексией.

Сохранение заключения вызывает это десятки раз. Если приложение запущено с другой рабочей папкой (ярлык с пустым «Рабочая папка», запуск из другого каталога), сохранение и разбор адресов DaData падают.

Исправление: `Core.NET` уже подключён ссылкой — вызывать `EnumExtension.GetEnumXmlAttributeValue` напрямую и закешировать соответствие «код → значение» для каждого типа.

### D-04. Падение при поиске организации в DaData — высокая

`ConclusionEdit.cs` стр. 1420–1421, `ConclusionBaseSettingEdit.cs` стр. 159–160:

```csharp
var splitsSplitsName = data.management?.name?.Split();
if (splitsSplitsName.Length >= 3)   // NullReferenceException, если management == null
```

У ИП и у части организаций DaData не возвращает `management`. Метод — `async void`, поэтому исключение уходит в обработчик WinForms и показывается окно «необработанное исключение». Там же `data.name.ToString()` падает при `name == null`.

Исправление: `if (splitsSplitsName?.Length >= 3)` и проверка `data.name`.

### D-05. Неверное определение региона — высокая

28 мест в 10 формах (`ConclusionEdit`, `DeclarantEdit`, `DesignerEdit`, `DeveloperEdit`, `AuthorEdit`, `TechnicalCustomerEdit`, `TechnicalCustomerENEdit`, `FundingInformationEdit`, `ConclusionBaseSettingEdit`, `ObjPartEdit`):

```csharp
GetEnumByAttributeValue<TRegionsRf>(addressData.region_kladr_id?.Replace("0", string.Empty))
```

`Replace` удаляет **все** нули из 13-значного кода КЛАДР:
- `5400000000000` → `54` — верно;
- `0100000000000` (Адыгея) → `1`, `5000000000000` (Московская обл.) → `5`, `7000000000000` (Томская обл.) → `7` — такого кода нет в `TRegionsRf`.

Ошибочно определяются регионы 01–09 и 10, 20, 30, 40, 50, 60, 70, 80, 90. Из-за D-02 метод не бросает исключение, поэтому `catch` с сообщением «Регион не определен» не срабатывает: молча записывается `"00"`.

Исправление: `region_kladr_id?.Substring(0, 2)` и явная проверка результата.

### D-06. Секреты DaData в исходном коде — высокая

`Core.NET/DaDataObj/DaDataObj.cs` стр. 9–10: API-ключ и секретный ключ лежат в коде и в истории git. Метод Clean платный, поэтому любой, у кого есть доступ к репозиторию или к собранной DLL, может тратить баланс.

Исправление: перевыпустить ключи в кабинете DaData, хранить их вне кода (настройка пользователя, `SettingXPO`, переменная окружения), удалить из исходников. Из истории git ключи не удалятся — поэтому нужен именно перевыпуск.

### D-07. Потеря данных объекта в пояснительной записке — высокая

`ExplanatoryNoteEdit.cs`: поле `_explanatoryNoteObjType` (стр. 29) меняется только в `cmbExplanatoryNoteObjType_SelectedValueChanged` (стр. 69).

- При загрузке тип в комбобоксе выставляется только для `tIndustrialObject`. Для `tNonIndustrialObject` и `tLinearObject` поля не загружаются, тип не выставляется, `_explanatoryNoteObjType` остаётся значением по умолчанию — `IndustrialObject`.
- При сохранении (стр. 404) создаётся **новый** `tIndustrialObject` с пустыми полями, и он заменяет `ExplanatoryNote.Item`.
- Если явно выбрать «Непроизводственный» или «Линейный», сохраняется пустой объект (`new tNonIndustrialObject()` / `new tLinearObject()`).

Сценарий: импортировать записку с линейным объектом, открыть, поправить номер и сохранить — сведения об объекте заменены пустым производственным объектом.

Исправление: до реализации форм для этих двух типов сохранять существующий `Item` без изменений и выставлять тип при загрузке.

### D-08. Застройщики в пояснительной записке — высокая

`ProjectDocumentation.NET/Models/ConclusionObj/PersonObj.cs`: `GetPersonObjByDeveloper` (стр. 39) вызывает `SetObjByDeclarator` (стр. 133), который распознаёт только `TDeclarant`. `tDeveloper` — другой тип (у него одно поле `Item`), поэтому:
- `Name` пустой — в таблице пустые строки;
- `BaseObj == null` — удаление (`obj.BaseObj is tDeveloper`) ничего не делает, правка открывает пустую `DeveloperEdit` и не меняет запись.

Исправление: добавить `SetObjByDeveloper`, разбирающий `tDeveloper.Item`.

### D-09. Таблица проектировщиков после удаления — средняя

`ConclusionEdit.cs` стр. 109: после удаления таблица строится через `GetPersonObj`, а не через `GetPersonObjByDesigner`. `SetObj` не обрабатывает `TDesigner`, поэтому у оставшихся строк пустые имена и `BaseObj == null`. До переоткрытия формы их нельзя изменить или удалить. Сохранению это не мешает: сохраняется `_tDesigners`.

Исправление: заменить вызов на `GetPersonObjByDesigner`.

### D-10. Молчаливая потеря данных при импорте — средняя

`Core.NET/Extensions/Utf8StringSerialize.cs`:
- если строгая десериализация не прошла, `NormalizeProblematicEnums` **удаляет** элементы восьми выводов с неизвестными значениями (стр. 182, 189) и не сообщает об этом пользователю. Словарь синонимов пуст;
- повторное чтение файла идёт через `File.ReadAllText(path, Encoding.UTF8)` (стр. 83), а не по кодировке из XML-декларации. Файл в `windows-1251` прочитается с искажением кириллицы;
- все исключения глотаются, наружу уходит только `null` — «Ошибка загрузки файла» без причины.

Исправление: возвращать список удалённых элементов и показывать его. Повторно читать с учётом декларации (`XmlReader`). Передавать текст исключения в сообщение.

### D-11. `null` вместо ошибки при сериализации — средняя

- `SerializeObject` при исключении возвращает `null`, а `StringToByte(null)` — `null`. Запись сохраняется с пустым `Obj` без предупреждения.
- `MainForm.EditGridViewObjectAsync`: если `GetConclusionByString` вернул `null` (повреждённый или пустой XML), открывается **пустая** форма (`Load` создаёт `new Conclusion()`). Её сохранение перезаписывает исходные данные.
- `barBtnBaseSetting_ItemClick` (стр. 327) при `conclusion == null` падает с `NullReferenceException` в `async void`.

Исправление: проверять результат, показывать ошибку и не открывать форму.

### D-12. Выгрузка XML — средняя

`MainForm.barBtnFill_ItemClick` (стр. 213): `<?xml-stylesheet … ?>` дописывается в **конец** файла, после корневого элемента. Браузеры применяют XSL только из пролога, поэтому стиль не подключится. Кроме того:
- `xsi:noNamespaceSchemaLocation` вставляется строковой заменой `xmlns:xsd`, а не через сериализатор;
- XML не проверяется по XSD — из-за D-02 и D-07 можно выгрузить невалидный документ.

Исправление: вставлять PI после XML-декларации (`XDocument.AddFirst` или `XmlWriter`) и проверять XML по XSD перед записью.

### D-13. Предпросмотр заключения — средняя

`Forms/ViewForm.cs`:
- стр. 38: `examinationResult.Replace(...)` при `null` (не нашли запись справочника) → `NullReferenceException`; так же `conclusion.ExaminationObject.*` при отсутствии раздела;
- фиксированный текст «заключение повторной негосударственной экспертизы» — независимо от формы и стадии;
- циклы разделов 1.4 и 1.6 пустые, а 1.4, 1.5 и 1.6 фильтруют один и тот же префикс `"03."` (стр. 100, 121, 141). Заявитель, функциональное назначение и ТЭП закомментированы;
- для пояснительной записки «Просмотр» ничего не делает.

Это незаконченный черновик функции. Его стоит либо доделать, либо скрыть кнопку.

### D-14. Создание схемы без ожидания — средняя

`Core.NET/Controllers/SessionController.cs` стр. 21, 34: `CreateDataBase` — `async void`, `GetSession` его не ждёт. На новой базе первые запросы могут пойти до `UpdateSchemaAsync`, а исключения создания схемы теряются.

Исправление: синхронные `CreateObjectTypeRecords()` и `UpdateSchema()` или `async Task` с ожиданием на старте.

### D-15. Зависимость от текущей папки — средняя

`SessionController` стр. 9: `"xml.s3db"` — относительный путь. При запуске не из каталога программы создаётся новая пустая база в другой папке, и пользователь «теряет» документы. То же для `Core.NET.dll` (D-03).

Исправление: строить пути от `AppDomain.CurrentDomain.BaseDirectory` или хранить базу в `%LocalAppData%`.

### D-16. Пояснительная записка: продолжительность и пожарная категория — средняя

`ExplanatoryNoteEdit.cs`:
- стр. 440: `ConstructionDuration` (decimal) разбирается через `int.TryParse` — `"1,5"` не разберётся и значение молча не изменится;
- стр. 226: при загрузке пожарная категория ищется по `GetEnumDescription()`. У `tFireDangerCategory` нет `Description`, поэтому для «Категория не устанавливается» сравнивается `Категориянеустанавливается` с `Категория не устанавливается`. Поле окажется пустым и при сохранении превратится в первое значение (D-02).

Исправление: `decimal.TryParse` с текущей культурой и сравнение по `GetEnumXmlAttributeValue()`.

### D-17. Невидимая потеря текста экспертов ПД — средняя

`ExpertProjectDocumentsEdit.cs` стр. 82–86, 229–230: поля «Описание основных решений» и «Сведения об оперативных изменениях» есть на форме, но их загрузка и сохранение закомментированы. Существующие значения в XML сохраняются, но введённый пользователем текст пропадает без предупреждения.

Исправление: либо вернуть привязку (с учётом формата RichEdit), либо скрыть поля.

### D-18. Обёртки строк в `async void` — средняя

`Models/ConclusionObj/DocumentObj.cs` стр. 31 и аналогичные `SetEnumObj` в `FinanceObj`, `ExpertProjectDocument`, `ExpertEngineeringSurvey`, `EngineeringSurveyAddress`, `ExplanatoryNoteObj/DocumentObj`:
- таблица получает массив сразу, а свойства (`DocName`, `DocTypeName` …) заполняются после `await` — ячейки могут остаться пустыми до следующей перерисовки;
- каждая строка — отдельный запрос в базу;
- исключения в `async void` не перехватываются;
- у `ExpertEngineeringSurvey` свойства `EngineeringSurveyChanges`, `…Conditions`, `…Methods`, `…ProgramNote` нигде не заполняются.

Исправление: синхронно заполнять из заранее загруженного справочника.

### D-19. Справочники — низкая

`DataBaseController` (стр. 21 и далее): категория заполняется, только если в ней нет записей. Исправления и новые значения в коде (например, обновлённый список документов) не дойдут до существующих баз. При первом запуске около 600 записей сохраняются по одной.

Исправление: версионировать справочники и обновлять по ключу `(вид, Value)`, сохранять пакетом через `UnitOfWork`.

### D-20. Обновления — низкая

`MainForm.CheckUpdates` (стр. 78–86): адрес по умолчанию — FTP по IP без шифрования, обновление обязательное (`Mandatory = true`), все исключения скрыты (`catch (Exception) { }`). Подмена ответа в сети даёт установку чужого exe.

Исправление: HTTPS, проверка подписи или хэша (AutoUpdater.NET это поддерживает), запись ошибок в журнал.

### D-21. GUID при импорте — низкая

Проверки на дубликаты нет: см. коммит «Убрана проверка на GUID при сохранении». Повторный импорт файла создаёт вторую запись с тем же GUID, и `LocateByValue` выделит первую. У пояснительной записки атрибут `id` при импорте игнорируется и при создании не заполняется.

### D-22. Неиспользуемый вспомогательный код — низкая

- `CRC32.ComputeHashFile(byte[])` и `ComputeHashString(string)` (стр. 47, 53): `chars.ToString().Reverse().ToString()` возвращает имя типа итератора, а не строку хэша.
- `AppExtensions.GetXORSum` (стр. 54) изменяет первый массив списка на месте и глотает ошибку длины.
- `AppExtensions.ReadStream` (стр. 13) требует `Stream.Length`, то есть не работает с сетевыми потоками.

Интерфейс этот код не вызывает — его можно удалить.

### D-23. Освобождение форм — низкая

Около 80 дочерних форм создаются через `new …Edit()` и `ShowDialog()` без `using` (например, `MainForm` стр. 248). Модальные формы DevExpress держат GDI-ресурсы до сборки мусора. За долгую сессию правки это может накапливаться.
